# 派工、取数与成稿

派工入口按本run实际发现的来源提供：`dispatch_business`、`dispatch_native`。每个入口一次提交一个小任务，正常取数只需两项：

```json
{"question": "取该客户端在原题时间窗内的延迟和请求率", "tools": ["insights_query_metrics"]}
```

程序继承已确认的对象范围、绝对时间窗和来源，生成任务/会话ID，并填写机械交付与停止条件。`tools` 只能从本入口列出的工具中选择；换来源时另调对应入口，不要把两套工具放进同一任务。

## 两种最短路径

- **纯取数**：对象、方向、绝对窗已由原题确定，一批查询能回答时，用 `first_result`（缺省）。把影响判断的指标放在同一批：同一路径的延迟、P95/P99 和请求率可放在同一次 `insights_query_metrics` 的 `metrics` 里；两条路径可在同一 Worker 工具响应中独立调用。程序在首批目标结算后交回原值、覆盖、单位和来源，Worker 不再另写小结。
- **需要研判**：要根据中间结果选择查询、消歧资源、关联不同来源或并行验证不同解释时，把子问题交给 Worker，并用 `return_mode="answer"`。

同一个简单题也可以直接调用 `query_business_metrics`：程序填入已确认的绝对窗和客户端 `auto_service_0` 过滤，不启动 Worker。对象必须逐字来自原题；服务端对象须来自原题或已返回的路径清单；试点只开放 `app-path`/`network-path`。结果为空、范围不符或需要进一步判断时，按实际状态交付缺口，或改用派工。

## 同刻比较

原题问尖峰、持续或同刻变化时，窗口聚合不能替代分钟时序。必须派 `insights_metric_history` 的 `first_result` 任务：少量已观察路径，分钟 `P95`/`P99`/`request_rate`，程序会交回统计、有效点和 `history_evidence` 候选。直查 `query_business_metrics` 只给窗口/路径汇总，不能回答尖峰形态。

先确认要比较的路径、方向和分钟口径。若都已确认，两条路径的同口径分钟查询可在同一 Worker 批次里独立执行，各自保留来源、单位和观察点；窗口聚合与分钟数据分别标明，分钟请求率保留统计口径。先看程序 facts 和 `history_evidence`；只有缺具体点时按 `source_id` 读取必要片段，不要反复读同一原文。程序会分别统计“两条路径同刻有值”和“两条路径各有前后相邻点而可比较涨幅”；0 个可比较时点只表示证据不足，不能写成证实没有同步变化。

更换对照路径是可选增益：只有原题需要同期比较、现有同口径样本不足、本次取证已给出有价值的候选、且剩余预算够补查和成稿时才做。补查后仍缺点时按现有证据交付，并写明缺哪条路径、指标或时点。

## 收尾

证据够用，或调查余量不足时，调用 `close_investigation` 主动结束取证。它不要和新的取证调用放在同一响应；程序会在批次结算的安全边界切换到生成预算，每次调查只启动一次专用成稿轮。

成稿默认只输出**一段**中文正文：第一句直接回答原题，随后给支撑结论的时间、关键数值和单位，最后说明会影响结论的覆盖缺口。不要分节、不要罗列工具或来源，不要编造；详细时序、原文指针和执行记录留在归档，可按 `source_id` 回查。

## 其他约束

收到阶段事实和缺口才继续；独立问题才并行，最新已返回任务可 `continue_task_id` 续作，改范围要另派。先读本地原文再下一轮派工，dispatch 之后不读取来改变依据。

派工被拒时按回执里的 `path` 和 `allowed_entry` 修正：坏 JSON 会明确说明参数未解析且尚未派工；字段错误指出具体路径；选错来源时错误里给出该工具自己的入口。保持原问题、窗口、禁查项，不改成全面体检，也不要重复相同调用。纠正有界，耗尽后直接说明阻断。

200 秒进入收尾后只汇总，不新派工；时间不足如实交有限结果，不把有正文当成任务完成。
