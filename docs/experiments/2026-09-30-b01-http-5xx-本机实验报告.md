# RCAgent 本机实验：查 checkout-0 的 HTTP 5xx

这次实验跑通了整条链：RCAgent 把问题交给本机 MCP Gateway，Gateway 再向 Mock Querier 取数据，RCAgent 最后给出了调查报告。它正确发现了 `checkout-0` 的 HTTP 5xx，也从 Trace 里发现 `payment-svc` 调用很慢。**`payment-svc` 值得优先查，但现有证据还不能证明它一定发生了故障。**

## 这次假故障是什么

Mock 选用 `b01-http-5xx` 场景，模拟订单服务 `checkout-0` 对外返回 5xx：

- 应用摘要给出 100 个请求、10 个错误，错误率 10%；异常样本里有 500、502、503。
- Pod 是 `Running`。TCP 建连失败率 0，重传率 1%，平均 RTT 10 毫秒；这些数据没有指向明显的 L4 网络故障。
- 一条 `/api/v1/orders` 请求耗时 1520 毫秒，其中 `payment-svc` 的 `POST /charge` Span 耗时 1350 毫秒，约占 88.8%。

这些是假数据源提供的**事实**。Mock 没有预先写好“根因是 payment-svc”的答案，判断仍由 Querier 的真实规则和 RCAgent 完成。场景定义见 [catalog.go](D:/kylin/kylin-insights-server-mainv6-mcp/kylin-insights/server/querier/grpc/diagnosis/scenario/catalog.go:30)。

运行命令是：

```bash

```

这条命令运行的是固定实验，不需要现场输入一段自然语言。脚本预先给了 RCAgent 一个调查任务：

| 输入 | 本次值 | 大白话解释 |
| --- | --- | --- |
| 集群 | `test-cluster` | 测试集群名 |
| 命名空间 | `b01-http-5xx` | 选择这组 Mock 故障数据 |
| 目标 Pod | `checkout-0` | 要调查的对象 |
| 故障描述 | `checkout-0` 正在返回 HTTP 5xx，请查证据并找可能的故障位置 | 给 Agent 的背景 |

输入写在 [run_mcp_mock_pipeline.py](D:/Business/Agents/RCAgent/local_testing/run_mcp_mock_pipeline.py:10)。模型使用本机已配置的 `deepseek-v4-flash`。

## RCAgent 做了哪些事

1. **初筛（Triage）**：解析 `checkout-0`，查 Pod 运行状态、网络摘要和应用摘要。它发现 10% 的 HTTP 错误，而 Pod 与 L4 网络指标看起来正常，于是把问题归到应用请求这一层继续查。
2. **列调查计划（Planner）**：计划了 4 件事：看应用错误、追一条错误请求、比较同工作负载的 Pod、做一次综合诊断。按默认每轮 3 个任务的设置，前三项先交给 Worker 并行处理。
3. **查证据（Worker）**：取回 5xx 请求样本，找到 Trace ID，再看请求经过哪些服务以及各段耗时；同时查同伴、网络和 Querier 的综合诊断结果。
4. **汇总（Supervisor）**：读完前三项的调查结果，输出最终报告。第 4 项任务在任务列表里仍是 `pending`，说明它没有作为单独任务被调度。

实际请求链是 `RCAgent → MCP Gateway :8888 → Mock Querier :19888 → Fake Provider`。Gateway 审计记录了 Tool 调用，Mock 的 Provider 日志也记录了 K8s、L4、L7、请求样本和 Trace 数据访问，因此这次不是 RCAgent 直接读取假数据。

输出中前三个任务仍显示 `in_progress`，这是最终任务状态没有同步刷新；报告已经生成，不能把它理解为这三个 Worker 还在运行。

| Gateway Tool | 次数 | 这次用来做什么 |

| `resolve_pod` | 5 | 找到目标 Pod 及其 UID，供后续查询使用 |
| `get_pod_runtime_status` | 1 | 确认 Pod 运行状态 |
| `get_pod_network_summary` | 3 | 看 TCP 建连、重传、RTT 和上下游 |
| `get_pod_application_summary` | 4 | 看 HTTP 请求量、错误率、耗时 |
| `get_abnormal_requests` | 3 | 取 5xx 样本和 Trace ID |
| `trace_request` | 2 | 看同一条错误请求的调用链 |
| `compare_pod_with_peers` | 1 | 尝试和同工作负载 Pod 对比 |

按阶段看，初筛调用了 4 次，Planner 补充上下文调用了 2 次，Worker 调查调用了 14 次。

这里有两个容易误读的点。`diagnose_pod` 虽然被列在第 4 个 `pending` 任务中，审计日志显示它已被某个执行中的 Worker 调用一次；任务里的 `suggested_tools` 目前只是建议，没有形成严格限制。`resolve_pod` 等工具重复调用，是多个并行 Worker 分别获取上下文，不代表有 5 个不同的 Pod。

## TTA：整次分析花了多久

**这次没有记录精确的完整 TTA。**实验脚本没有在开始运行和最终报告产生时打时间戳，粘贴的终端输出也没有这两个时间点。

能从 Gateway 日志直接核实的是：首个 Tool 调用发生在 **09:01:33**，最后一个发生在 **09:03:20**，两者相隔 **1 分 47 秒**。所以完整分析至少用了 1 分 47 秒；它还包含第一次 Tool 调用前的启动与模型思考，以及最后一次 Tool 调用后的报告生成，实际 TTA 更长。

20 次 Gateway 处理调用的 `duration_ms` 合计约 **123 毫秒**，单次最长 **59 毫秒**。这只反映 Gateway 处理 Tool 的时间，不能拿来当整次分析耗时。Trace 中的 **1520 毫秒**则是 Mock 里一条业务请求的耗时，也不是 RCAgent 的 TTA。

## 最后得到了什么结论

RCAgent 的原始报告将故障定位为：`payment-svc` 的 `POST /charge` 失败或超时，拖慢 `checkout-0`，导致它向 `gateway-0` 返回 5xx；输出 `status: passed`。

其中有依据的部分是：

- `checkout-0` 确实有 10% HTTP 错误；
- 抽样 Trace 确实显示 `payment-svc` 占用了这条请求约 88.8% 的耗时；
- `checkout-0` 的 L4 网络指标正常。

需要保留问号的部分是：

- Trace 只有耗时，没有给出 `payment-svc` 自身的错误码或超时事实；不能直接断言它已经失败。
- 500/502/503 说明请求失败，不能单凭状态码排除 `checkout-0` 自身的代码或错误处理问题。
- Mock 的 Peer 列表只有 `checkout-0`，但 Service Endpoint 数设置为 3；不能从“没拿到 Peer”推断线上只有一个副本。Mock 提供的网络下游是 `mysql-0`，Trace 则出现 `payment-svc`，目前还缺两者完整的拓扑说明。

因此更稳妥的实验结论是：**这是 `checkout-0` 入口 5xx 故障；`payment-svc` 是应优先核查的慢调用，真正故障点仍需它自己的请求状态和更多 Trace 证据确认。**`status: passed` 在当前脚本里只表示生成了最终报告，不是“根因已被证明”的评分。

## 这次实验说明了什么，还差什么

链路和编排已经跑通：Triage、Planner、并行 Worker、Supervisor 都完成了工作，并真实使用本机 Gateway 的 Tool。当前主要短板是 **Mock 的 Peer/拓扑数据不够完整**，以及 **Agent 把“最可能的线索”写成了“已证实的根因”**。后续比较有价值的改进，是让 Mock 的 Pod/Endpoint/调用关系一致，并给实验脚本加入起止计时和 Tool 调用明细，下一次就能直接给出精确 TTA。

终端开头的 LangChain 弃用提醒和 Pydantic 序列化提醒没有中断这次运行；它们是后续升级依赖时需要处理的兼容性提醒。
